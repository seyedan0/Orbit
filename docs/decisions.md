# تصمیم‌های معماری و فنی

برای هر تصمیم مهم یک رکورد اضافه کنید. تصمیم‌های قبلی را حذف نکنید؛ اگر تصمیمی تغییر کرد، دلیل تغییر را ثبت کنید.

## قالب تصمیم

```md
## ADR-001: عنوان تصمیم

- **تاریخ:** YYYY-MM-DD
- **وضعیت:** پیشنهادی | پذیرفته‌شده | جایگزین‌شده
- **زمینه:** چه مسئله‌ای وجود داشت؟
- **تصمیم:** چه چیزی انتخاب شد؟
- **دلیل:** چرا این گزینه انتخاب شد؟
- **پیامدها:** مزایا، هزینه‌ها و محدودیت‌ها
- **جایگزین‌ها:** گزینه‌های بررسی‌شده
```

## ADR-001: مستندات‌محور شروع می‌شوند

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** پروژه هنوز پشته فنی، دامنه دقیق و معماری مشخصی ندارد.
- **تصمیم:** ابتدا قرارداد ثبت پیشرفت و ساختار مستندات ایجاد شود.
- **دلیل:** همکاری چند AI بدون منبع وضعیت مشترک باعث تکرار کار و از دست‌رفتن تصمیم‌ها می‌شود.
- **پیامدها:** شروع توسعه فنی به تعریف MVP و انتخاب پشته فنی وابسته می‌ماند.
- **جایگزین‌ها:** شروع مستقیم با یک فریم‌ورک مشخص، که فعلاً به‌دلیل نبود نیازمندی کافی رد شد.

## ADR-002: مونو‌ریپو به‌صورت مرحله‌ای ایجاد می‌شود

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** محصول باید سه کلاینت و چند پکیج مشترک داشته باشد، اما کد اجرایی هنوز وجود ندارد.
- **تصمیم:** ابتدا workspace ریشه و قراردادهای مشترک ایجاد شود؛ سپس اسکلت اپ‌ها و در ادامه vertical slice سینک ساخته شود.
- **دلیل:** قراردادها پیش از UI و زیرساخت تثبیت می‌شوند و از ایجاد سه پیاده‌سازی ناسازگار جلوگیری می‌کنند.
- **پیامدها:** راه‌اندازی اولیه کمی زمان بیشتری می‌گیرد، اما تغییرات مدل داده کنترل‌شده‌تر خواهد بود.
- **جایگزین‌ها:** ساخت مستقل هر اپ، یا ایجاد کامل همه اپ‌ها پیش از قراردادهای shared.

## ADR-003: سرور MVP با NestJS و PostgreSQL طراحی می‌شود

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** سینک به API، تراکنش، ذخیره‌سازی پایدار و مسیر رشد مشخص نیاز دارد.
- **تصمیم:** Node.js + NestJS برای API و PostgreSQL برای منبع حقیقت سرور استفاده شود.
- **دلیل:** ساختار ماژولار NestJS برای تیم چندنفره و قراردادهای HTTP/WebSocket مناسب است و PostgreSQL نیازهای رابطه‌ای و نسخه‌بندی را پوشش می‌دهد.
- **پیامدها:** نگهداری migration و زیرساخت سرور ضروری است؛ انتخاب نهایی ORM در طراحی اجرایی ثبت خواهد شد.
- **جایگزین‌ها:** Fastify خام، SQLite روی سرور یا سرویس backend آماده.

## ADR-004: قرارداد داده از دیتابیس محلی مستقل می‌ماند

- **تاریخ:** 2026-09-29
- **وضعیت:** پیشنهادی
- **زمینه:** SQLite و WatermelonDB هرکدام مزایا و محدودیت‌های متفاوتی برای دسکتاپ و موبایل دارند.
- **تصمیم:** ابتدا مدل منطقی، schema و interface مستقل تعریف شود؛ انتخاب implementation محلی بعد از ارزیابی عملکرد، migration و پشتیبانی آفلاین انجام شود.
- **دلیل:** تصمیم زودهنگام درباره ابزار محلی نباید قرارداد مشترک را به یک کتابخانه قفل کند.
- **پیامدها:** یک لایه adapter لازم خواهد بود و انتخاب دیتابیس در فاز طراحی باقی می‌ماند.
- **جایگزین‌ها:** WatermelonDB از ابتدا برای موبایل، یا SQLite خام برای همه کلاینت‌ها.

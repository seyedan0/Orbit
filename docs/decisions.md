# تصمیم‌های معماری و فنی

برای هر تصمیم مهم یک رکورد اضافه کنید. تصمیم‌های قبلی را حذف نکنید؛ اگر تصمیمی تغییر کرد، دلیل تغییر را ثبت کنید.

## قالب تصمیم

```md
## ADR-001: عنوان تصمیم

- **تاریخ:** YYYY-MM-DD
- **وضعیت:** پیشنهادی | پذیرفته‌شده | جایگزین‌شده
- **زمینه:** چه مسئله‌ای وجود داشت؟
- **تصمیم:** چه چیزی انتخاب شد؟
- **دلیل:** چرا این گزینه انتخاب شد؟
- **پیامدها:** مزایا، هزینه‌ها و محدودیت‌ها
- **جایگزین‌ها:** گزینه‌های بررسی‌شده
```

## ADR-001: مستندات‌محور شروع می‌شوند

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** پروژه هنوز پشته فنی، دامنه دقیق و معماری مشخصی ندارد.
- **تصمیم:** ابتدا قرارداد ثبت پیشرفت و ساختار مستندات ایجاد شود.
- **دلیل:** همکاری چند AI بدون منبع وضعیت مشترک باعث تکرار کار و از دست‌رفتن تصمیم‌ها می‌شود.
- **پیامدها:** شروع توسعه فنی به تعریف MVP و انتخاب پشته فنی وابسته می‌ماند.
- **جایگزین‌ها:** شروع مستقیم با یک فریم‌ورک مشخص، که فعلاً به‌دلیل نبود نیازمندی کافی رد شد.

## ADR-002: مونو‌ریپو به‌صورت مرحله‌ای ایجاد می‌شود

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** محصول باید سه کلاینت و چند پکیج مشترک داشته باشد، اما کد اجرایی هنوز وجود ندارد.
- **تصمیم:** ابتدا workspace ریشه و قراردادهای مشترک ایجاد شود؛ سپس اسکلت اپ‌ها و در ادامه vertical slice سینک ساخته شود.
- **دلیل:** قراردادها پیش از UI و زیرساخت تثبیت می‌شوند و از ایجاد سه پیاده‌سازی ناسازگار جلوگیری می‌کنند.
- **پیامدها:** راه‌اندازی اولیه کمی زمان بیشتری می‌گیرد، اما تغییرات مدل داده کنترل‌شده‌تر خواهد بود.
- **جایگزین‌ها:** ساخت مستقل هر اپ، یا ایجاد کامل همه اپ‌ها پیش از قراردادهای shared.

## ADR-003: سرور MVP با NestJS و PostgreSQL طراحی می‌شود

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** سینک به API، تراکنش، ذخیره‌سازی پایدار و مسیر رشد مشخص نیاز دارد.
- **تصمیم:** Node.js + NestJS برای API و PostgreSQL برای منبع حقیقت سرور استفاده شود.
- **دلیل:** ساختار ماژولار NestJS برای تیم چندنفره و قراردادهای HTTP/WebSocket مناسب است و PostgreSQL نیازهای رابطه‌ای و نسخه‌بندی را پوشش می‌دهد.
- **پیامدها:** نگهداری migration و زیرساخت سرور ضروری است؛ انتخاب نهایی ORM در طراحی اجرایی ثبت خواهد شد.
- **جایگزین‌ها:** Fastify خام، SQLite روی سرور یا سرویس backend آماده.

## ADR-004: قرارداد داده از دیتابیس محلی مستقل می‌ماند

- **تاریخ:** 2026-09-29
- **وضعیت:** پیشنهادی
- **زمینه:** SQLite و WatermelonDB هرکدام مزایا و محدودیت‌های متفاوتی برای دسکتاپ و موبایل دارند.
- **تصمیم:** ابتدا مدل منطقی، schema و interface مستقل تعریف شود؛ انتخاب implementation محلی بعد از ارزیابی عملکرد، migration و پشتیبانی آفلاین انجام شود.
- **دلیل:** تصمیم زودهنگام درباره ابزار محلی نباید قرارداد مشترک را به یک کتابخانه قفل کند.
- **پیامدها:** یک لایه adapter لازم خواهد بود و انتخاب دیتابیس در فاز طراحی باقی می‌ماند.
- **جایگزین‌ها:** WatermelonDB از ابتدا برای موبایل، یا SQLite خام برای همه کلاینت‌ها.

## ADR-005: Web اولین کلاینت محصول است

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** توسعه هم‌زمان Web، Desktop و Android هزینه هماهنگی و ریسک اختلاف تجربه را بالا می‌برد.
- **تصمیم:** Web اولین کلاینت قابل استفاده و مرجع رفتاری Orbit باشد؛ Desktop و Android بعد از تثبیت Web، قراردادها و sync توسعه پیدا کنند.
- **دلیل:** Web سریع‌تر قابل انتشار و آزمایش است و برای اعتبارسنجی UX، task flow، Pomodoro و analytics بازخورد زودتری می‌دهد.
- **پیامدها:** storage مرورگر و محدودیت‌های Web باید زود طراحی شوند؛ قابلیت‌های native مانند widget و notification کامل به فازهای بعد منتقل می‌شوند.
- **جایگزین‌ها:** شروع هم‌زمان سه اپ یا شروع با Desktop به‌عنوان کلاینت اصلی.

## ADR-006: پشته Web شامل Vite، React و React Router است

- **تاریخ:** 2026-09-29
- **وضعیت:** پذیرفته‌شده
- **زمینه:** فاز ۱ به اسکلت Web قابل اجرا با routing، layout و auth boundary نیاز دارد و معماری React را برای Web و Desktop (Tauri) پیش‌بینی کرده است.
- **تصمیم:** `apps/web` با Vite، React 19، React Router و Vitest ساخته شود. auth boundary فعلاً یک نشست محلی موقت است و storage ابتدا adapter حافظه‌ای و سپس IndexedDB برای پورت `AtomicTaskStore` است.
- **دلیل:** Vite برای SPA local-first کافی و سبک است و اشتراک کد React با Tauri را ساده نگه می‌دارد.
- **پیامدها:** نشست محلی موقت است و در فاز ۳ جایگزین می‌شود؛ SSR در محدوده نیست. `vitest` باید روی نسخه ۵ یا بالاتر بماند.
- **جایگزین‌ها:** Next.js (SSR غیرضروری برای local-first)، Remix، یا شروع بدون Vite.

## ADR-007: storage پایدار Web با IndexedDB و قرارداد AtomicTaskStore

- **تاریخ:** 2026-09-30
- **وضعیت:** پذیرفته‌شده
- **زمینه:** فاز ۲ به storage پایدار Web نیاز دارد؛ پورت اولیه `LocalStore` عملیات اتمیک «ذخیره entity + ثبت mutation» را در یک تراکنش بیان نمی‌کرد، در حالی که معماری ثبت هم‌زمان و اتمیک entity و mutation را الزامی می‌داند.
- **تصمیم:** پورت `AtomicTaskStore` با متد `saveTaskWithMutation` به `sync-engine` اضافه شود و در `apps/web` با استفاده از `idb` از طریق `IndexedDbLocalStore` پیاده‌سازی شود؛ ثبت task و mutation در یک تراکنش اتمیک IndexedDB انجام می‌شود و در صورت تکرار `idempotencyKey`، ثبت mutation رد شده اما task ذخیره می‌شود.
- **دلیل:** IndexedDB استاندارد پایدار و transactional در مرورگرهاست و `idb` تایپ‌های مناسب بر روی آن ارائه می‌دهد بدون اینکه منطق دامنه به IndexedDB وابسته شود.
- **پیامدها:** داده‌ها پس از رفرش مرورگر باقی می‌مانند. کلاینت‌های آینده (Desktop با SQLite و Android) قرارداد مشترک `AtomicTaskStore` را پیاده خواهند کرد.
- **جایگزین‌ها:** localStorage (فاقد تراکنش و ظرفیت کم)، OPFS/WASM SQLite (پیچیدگی غیرضروری برای این فاز).

## ADR-008: انتخاب TypeORM برای پایگاه داده PostgreSQL سرور NestJS

- **تاریخ:** 2026-09-30
- **وضعیت:** پذیرفته‌شده
- **زمینه:** در فاز ۳ و پیرو ADR-003، هسته سرور با NestJS و پایگاه داده PostgreSQL پیاده‌سازی می‌شود. برای نگاشت موجودیت‌های دامنه، ایجاد و اجرای مایگریشن‌ها، تضمین تراکنش‌های اتمیک در عملیات همگام‌سازی (`push`) و ارتباط پایدار با دیتابیس (مانند Neon PostgreSQL)، نیاز به انتخاب ORM یا Query Builder بود.
- **تصمیم:** استفاده از `@nestjs/typeorm` و `typeorm` همراه با درایور `pg`.
- **دلیل:**
  1. یکپارچگی بومی و درجه یک با سیستم تزریق وابستگی (DI) و معماری ماژولار NestJS.
  2. امکان تعریف مستقیم موجودیت‌ها با دکوراتورهای استاندارد TypeScript منطبق بر `docs/data-model.md`.
  3. پشتیبانی ساده و قدرتمند از تراکنش‌های اتمیک دیتابیس (`dataSource.transaction`) برای ثبت هم‌زمان entity و mutation در عملیات push.
  4. عدم نیاز به موتورهای باینری اختصاصی یا مراحل تولید کد اضافی در ساختار monorepo.
  5. مدیریت شفاف schema migrationها و تطابق کامل با استانداردهای سازمانی NestJS.
- **پیامدها:** موجودیت‌های دیتابیس تحت `apps/server/src/database/entities/` ایجاد شده و `PostgresSyncRepository` با استفاده از `DataSource` و تراکنش‌های TypeORM پیاده‌سازی می‌شود.
- **جایگزین‌ها:**
  - Prisma: نیازمند مرحله تولید کد (`prisma generate`) و باینری‌های مجزا در monorepo.
  - Drizzle / Kysely: انتزاع مناسب اما یکپارچگی کمتر با اکوسیستم DI در NestJS نسبت به TypeORM.
  - raw `pg`: فاقد مدیریت ساختاریافته مدل‌ها و مایگریشن‌ها.
